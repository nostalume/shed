# Working agreements

Work from the user's goal and the project's actual conditions. Keep established
requirements, observed behavior, approved designs, and unresolved questions
distinct. Inspect existing material before asking the user to reconstruct it.

Keep each change directed at the requested result. Preserve unrelated user work
and avoid speculative features or process. Choose implementation details from the
current problem; do not treat past code structure as a permanent requirement.

The [DSL specification](DSL.md) owns the approved next-language semantics.
The [development plan](../plans/dsl-development.md) owns implementation sequencing
and progress. The README describes the current interface and implementation limits.
Do not present a planned capability as already implemented.

Use evidence appropriate to the changed claim. Report completed checks, meaningful
limitations, and remaining work candidly. If new evidence contradicts a design
premise, reopen the affected decision rather than accumulating compensating fixes.

Implementation-specific rules belong with the code or the scoped change that
requires them, not in this standing collaboration document. Publication, releases,
and changes to external systems remain separate from local development authority.
